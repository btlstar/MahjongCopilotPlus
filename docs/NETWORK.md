# 资源下载与直连排查

## 一番街实验性链路

一番街使用原生进程捕获，默认经过 Copilot HTTP 10999，可选再经过外部 RiichiCityUnlock HTTP 41110。自动捕获入口仅限本次启动客户端与子进程，本机 IPC 直连，不改系统代理；未启用解锁时可配置独立的一番街上游地址。AI 推理仍与游戏代理分开。外部工具的 CA、启动日志、手动分流与验证边界见[一番街说明](RIICHICITY.md)。

以下浏览器和资源下载说明主要针对雀魂。

## 代码中的下载路径

程序启动的 Chromium 使用本地 mitmproxy，以捕获对局 WebSocket 并应用 MajsoulMax 修改。

```text
Chromium → 本地 mitmproxy → 上游代理（如有）→ 游戏服务器／资源 CDN
```

“设置 → 连接 → 连接与代理”中的上游代理留空时，mitmproxy 自行建立连接。程序没有额外的带宽限速、资源逐个下载队列或固定 140 KB/s 限制。浏览器使用持久化资料目录，代码没有禁用 HTTP 缓存，也没有安装会关闭缓存的 Playwright 请求路由。

## 仅使用 Copilot 拦截并直连

1. 打开“设置 → 连接 → 连接与代理”，关闭“使用上游代理”，保存。关闭后会清空已保存的上游地址，避免继续连接停用的本机代理端口。
2. 保留 Copilot 本地端口，默认 `10999`。它用于捕获对局，与 Clash 等软件的上游端口不同。
3. 关闭程序启动的游戏浏览器，再点击“打开游戏”。连接设置会在浏览器关闭后应用，重新打开才使用新路径。
4. 在“诊断”查看当前路径；本地代理未启动时显示的是已保存路径。预期路径为“Copilot → 游戏服务器（直连）”。

本项目不修改 Windows 系统代理、其他代理软件或 TUN 设置。若希望整条游戏链路不经过其他代理软件，需要同时确认那些软件已停止接管该流量。AI 连接与游戏拦截是两条独立路径。

## 502 与间歇断网

如果所有网站在程序浏览器中都返回 502，先检查旧上游代理是否仍在运行，而非反复重装证书或调整标签页。`WinError 1225`／`10061` 表示连接被拒绝；当 Copilot 仍配置为向已停用的本机代理端口转发时，就可能出现这一情况。

浏览器生命周期已修复：打开失败、502 或刷新过程中的临时 JS 环境销毁不会再使程序主动关闭窗口。网络恢复后，可在同一标签页刷新；提示层会随新文档恢复。真正关闭游戏标签页／浏览器或退出程序时，仍正常清理所属浏览器。此修复处理的是程序误关窗口，不能保证 Chromium 自身永不崩溃，也不替代对线路的排查。

新的诊断信息会记录最近一次 HTTP 转发失败的时间、目标主机及错误类别，以及 WebSocket 关闭时间、关闭方、状态码与已连接时长。只记录主机与连接元数据，不记录请求参数、代理凭据或牌局消息；同一类短时间重复失败会合并日志输出。

这些信息用于区分连接被拒绝、域名解析失败、超时和连接被重置。WebSocket 的关闭方和状态码是观察结果，不能单独证明根因。如果再次出现约一分钟的断网，保留该时段的诊断与日志，同时比较普通浏览器是否断网，再判断是本地拦截、原上游代理、系统网络或游戏连接的问题；短时资源请求成功不能证明长时间对局稳定。

本地捕获代理仍有连接、TLS 与处理开销，不能等同于浏览器完全不经过代理的路径。

## 这次的改动

以前仅设置 `stream_large_bodies='256k'`，小响应仍可能先完整缓冲。现在在收到普通 HTTP 响应头时即启用流式转发，包括小文件和未知正文长度的分块响应。此项目只修改 WebSocket 消息，普通 HTTP 正文无需保留。

HTTP 101 协议升级保留原处理方式，捕获、AI 消息与本地装扮修改继续工作。不增加磁盘缓存，不改动 CDN 地址、内容编码或资源版本。实现依据见 [mitmproxy Streaming](https://docs.mitmproxy.org/stable/overview/features/#streaming)。

离线测试使用实际本地 HTTP 服务器和 mitmproxy：源站发出前 4 字节后暂停，验证浏览器侧可先收到数据，再继续完成响应。覆盖小于原阈值的固定长度响应及未知大小的分块响应。这证明缓冲等待已移除，**不证明真实 CDN 的下载带宽会提高**。

## TUN 与客户端分流

TUN 可以在网络层接管应用流量；程序上游代理留空并不能绕过 TUN。是否走机场取决于规则模式、命中的出站策略及 DNS 配置。即使命中 DIRECT，也可能经过 TUN 的处理与 DNS。参考 [TUN](https://wiki.metacubex.one/config/inbound/tun/)、[路由规则](https://wiki.metacubex.one/config/rules/) 和 [DNS 配置](https://wiki.metacubex.one/config/dns/)。

### AkagiOT／Akagi v3 的应用层直连

Akagi 的连接测试、授权检查、模型列表和实际推理共用“应用层直连”策略，不自动继承 HTTP_PROXY／HTTPS_PROXY／ALL_PROXY 或 Requests 自动读取的系统代理。旧版 OT 推理复用自己的直连会话。该策略与 Copilot 的游戏上游代理互相独立，也不会改变其他 AI 来源的代理行为。

这不能绕过系统层的 TUN。机场专属客户端未必使用 Mihomo，也不能直接套用下面的 YAML。对于提供规则界面的客户端，在其自定义分流中为 `mjapi.shinkuan.me`、`server.akagiot.org` 设置“直连”，并核对规则优先级与实际出站。优先使用完整域名匹配；只有关键词选项时，填写完整主机名并确认它确实命中需要的连接。游戏域名如 `game.maj-soul.com` 可独立配置，其他资源域名以实际连接为准。具体匹配方式和规则是否会被订阅覆盖，以客户端实现为准。

### Mihomo 客户端的规则示例

使用 Clash Verge、Mihomo Party、FlClash 等 Mihomo 客户端时，选择“规则模式”，将下面两条规则插入现有规则列表最前面，放在宽泛的 RULE-SET、GEOIP、MATCH 等规则之前；保留原有其他规则：

```yaml
mode: rule
rules:
  - DOMAIN,mjapi.shinkuan.me,DIRECT  # Akagi v3
  - DOMAIN,server.akagiot.org,DIRECT # 旧版 OT
  # 继续保留你的其余规则
```

这是合并片段，不是完整订阅配置。使用客户端的自定义／覆写规则功能持久化修改，避免订阅更新将它覆盖。全局代理模式不按这份规则分流；上述 DOMAIN 规则匹配完整域名，与所选模型 ID 无关。若手动更换了 AI 服务地址，需要对新地址的主机名添加 DIRECT 规则。

保存并重新加载代理配置后，重启 Copilot，使旧 HTTP 连接池关闭。在代理客户端的“连接”面板确认 AI 域名最终命中 DIRECT，再分别测试连接与对局推理。DIRECT 表示不走代理节点，流量仍可能由 TUN 管理；本项目不会自动修改你的代理软件配置。

如果已经命中 DIRECT 但仍无建议，在 Copilot“诊断”查看是否为推理超时、DNS／TLS 错误或服务端错误。v3 管理检查的连接／读取超时设为 8 秒；推理除了套接字超时外，还限制调用方单次总等待最多约 3 秒。该上限包含 DNS、连接、同源重定向与正文读取，避免把套接字的 3 秒误当作总耗时上限。立直需要两次推理，两次分别受限；连接测试成功并不保证实际推理及时完成。

超时后释放“计算中”并显示建议异常，迟到结果不回填当前或后续建议。底层 DNS 等网络操作无法由 Python 安全强行终止，后台可能仍在收尾；同一客户端在其结束前不会再排队发送推理，会提示“上次网络请求仍未结束”。网络操作结束后，下一次合法决策以最新的本局历史重新请求。该机制不自动重试、不修改游戏连接、不切换模型。单次超时本身不足以证明根因是 TUN。

状态栏的“已核验”和诊断中的逐次模型记录可用于区分“请求失败”与“返回型号不符”；旧日志未记录服务端模型 ID 的历史决策不能事后补证。新日志新增的核验元数据不包含密钥或牌谱，但原有完整运行日志仍可能包含游戏数据，分享前请检查。

### 游戏资源直连

如果希望资源直连，可在规则模式下将已确认的域名加入优先级足够高的 DIRECT 规则，例如：

```yaml
rules:
  - DOMAIN,game.maj-soul.com,DIRECT
  # 其余规则保持自己的配置
```

这是插入现有规则列表的示例，不是完整配置。若下载跳转到其他 CDN 域名，需在连接面板核对实际命中规则；单独这一条不能保证所有资源直连。本文不修改你的代理客户端配置。

## 如何比较

1. 在程序中将上游代理留空。若刚改动连接设置，先关闭并重新打开游戏浏览器。
2. 选择**同一个实际资源 URL**，分别比较 TUN 关闭、TUN 开启且命中 DIRECT，以及确有必要时的代理节点。域名首页的加载速度不能代表皮肤资源的下载吞吐。
3. 在代理客户端可用的连接／日志面板确认最终域名与出站链，比较 DNS／CDN IP、首字节耗时和持续传输速度。使用浏览器开发者工具测试时统一缓存条件；正常游玩时保留缓存。
4. 使用相同资源、缓存条件和线路，再比较程序浏览器与普通浏览器。这样可以判断慢在 CDN／网络路径，还是本地捕获代理。

仅凭一次下载速度无法判断瓶颈；应使用相同资源、缓存条件和线路比较，分别排查源站、CDN、代理与运营商路径。
